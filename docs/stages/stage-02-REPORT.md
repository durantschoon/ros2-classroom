**Mutation 6 caught a hole in the harness itself, and that is why it is worth
reading.** The first time it ran, *nothing failed*: the harness captured
subprocess output with `universal_newlines=True`, whose newline translation
silently rewrites `\r\n` to `\n` — so the test that exists to prove the carriage
return is stripped could never see one. The harness now captures bytes and
decodes them by hand, and `Run.out_lines` splits on `\n` only rather than using
`str.splitlines()`, which would also split on a lone `\r`. Mutation 6 was then
re-run and failed 4 tests. Mutations 1–5 were re-run against the fixed harness
too; the table above is the final run of all six.

## 5. Observable behaviour the prompt's list missed

Everything below was found by reading the script and is pinned unless stated.

### `compose-command`

- **An unknown mode falls through to the default.** `compose-command --bogus`
  prints the compose command, because the final `case` has a `*)` arm. Pinned
  (`test_an_unknown_mode_behaves_like_the_default`) — a port that used
  `argparse` with a strict choice list would change this.
- **On success, nothing is written to stderr.** Pinned; the Makefile captures
  stdout from `--make` and would otherwise inherit noise.
- **When nothing is found, every mode exits 1**, including `--engine` and
  `--make`, which print nothing at all (they fall into the `*)` arm of the
  failure `case` and emit the one-line hint on stderr). Pinned.
- **The v1 `docker-compose` binary reports `docker` as the engine.** Pinned.

### `compose-up`

- **`IMAGE_NAME` and `ROS_DISTRO` change which image is inspected**
  (`${IMAGE_NAME:-ros2-tutorials}:${ROS_DISTRO:-lyrical}`). Pinned.
- **The container lookup hardcodes the project name.** The filters are exactly
  `label=com.docker.compose.project=ros2-tutorials` and
  `label=com.docker.compose.service=desktop`, in that order, and do not follow
  `SELFTEST_PROJECT` or `-p`. Pinned as today's behaviour; raised under Open
  questions.
- **The compose command's exit status is the script's**, because the last line
  is `exec`. Pinned.
- **Only one `ps` call is made.** Pinned, as the assertion that the lookup is a
  single query rather than a loop.

### `run-quiet`

- **`VERBOSE` must be exactly `1`.** `VERBOSE=0`, and any other value, still
  filters. Pinned.
- **Arguments reach the wrapped command unchanged**, including flags that look
  like `run-quiet`'s own. Pinned.
- **The exit status survives the `VERBOSE=1` path too** (a different code path:
  `exec "$@"` rather than the filtering pipeline). Pinned.

### `open-url`

- **A missing URL is a usage error**: `${1:?usage: open-url URL}` writes
  `usage: open-url URL` to stderr and exits non-zero (2 under dash). Pinned.
- **The chosen opener replaces the script**, so `wslview`'s exit status becomes
  `open-url`'s — while `explorer.exe`'s is deliberately swallowed. Pinned
  (`test_the_opener_replaces_the_script_so_its_status_is_the_status`); the
  asymmetry is raised under Open questions.
- **`BROWSER` wins even on WSL**, before `is_wsl` is consulted at all. Pinned.
- **On WSL with no opener, stdout is exactly the URL and one newline** — the
  fallback sentence goes to stderr, so `$(open-url "$u")` is still just the URL.
  Pinned.

### `check-host`

- **The version probe has a fallback**: when `<engine> version --format
  '{{.Client.Version}}'` fails, `<engine> --version | head -1` is used, and that
  whole line is printed after `engine:  `. Pinned.
- **Docker is never probed for rootlessness** — the rootless check is inside
  `if [ "${engine}" = 'podman' ]`. Pinned.
- **Everything goes to stdout, including the failure path**; stderr stays empty
  even when the exit status is 1. Pinned.
- **Section order is fixed**: `Container engine`, then `Resources`, then the
  verdict. Pinned.
- Not pinned: the exact disk/memory thresholds' wording beyond `ok`/`warn` and
  `<N> GB`, because the numbers are the machine's.

### `base-image-digest`

- **The token URL is exact**:
  `https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/ros:pull`,
  fetched with `-fsS` and nothing else. Pinned.
- **Both multi-arch media types are sent**, as two separate `Accept` headers
  (OCI index and Docker manifest list). Pinned — a port that sent one would
  still work against Docker Hub today and break on an OCI-only registry.
- **The token is sent as `Authorization: Bearer <token>`.** Pinned.
- **The header match is only *partly* case-insensitive.** The sed pattern
  `s/^[Dd]ocker-[Cc]ontent-[Dd]igest: //p` varies the first letter of each word
  only, so `Docker-Content-Digest` and `docker-content-digest` both match but
  `DOCKER-CONTENT-DIGEST` does not. Pinned as today's behaviour in
  `test_an_all_uppercase_header_is_not_matched_today`, and raised under Open
  questions.
- **A failing `curl -I` produces the "no digest" message**, not a
  network-specific one. Pinned.

## 9. Open questions

1. **`compose-up` hardcodes the compose project name.** Its container lookup
   filters on `com.docker.compose.project=ros2-tutorials`, so under
   `SELFTEST_PROJECT=…` or any `-p` override it finds no container and never
   detects a stale image — the exact failure `compose-up` exists to prevent.
   Pinned as-is. Should the port read the project from the environment, or is
   the student's single project the only case that matters?
2. **`base-image-digest`'s header match is not truly case-insensitive.** HTTP
   header names are case-insensitive by RFC 9110, but
   `s/^[Dd]ocker-[Cc]ontent-[Dd]igest: //p` misses `DOCKER-CONTENT-DIGEST` and
   every other casing beyond the two conventional ones. Today Docker Hub sends
   `Docker-Content-Digest`, so nothing is broken. Pinned as today's behaviour in
   a test whose name says so. A Python port would naturally get this right; that
   would be a user-visible improvement, which guardrail 8 says is a STOP AND ASK.
3. **`open-url` swallows `explorer.exe`'s exit status but propagates
   `wslview`'s and `powershell.exe`'s** (they are `exec`'d). Deliberate for
   `explorer.exe`, which exits non-zero on success — but it means `open-url` can
   still exit non-zero on a path where the URL *was* opened. The script's own
   header says every failure mode should leave the user able to copy the
   address, and it does; only the status is inconsistent.
4. **Guardrail 7 is satisfied by a dependency, not by `pkg`.** `pkg new` on an
   existing package refuses only because `ros2 pkg create` refuses, so the
   student sees ros2's wording (`Aborted! / The directory already exists: …`)
   and `pkg`'s own `+ ros2 pkg create …` line is printed first, implying the
   command is about to succeed. The Stage 03 port must either keep relying on
   `ros2 pkg create` for this or add an explicit check — the second would change
   user-visible output.
5. **`tests/host/**` is not linted.** `scripts/lint-scripts` discovers only
   `scripts/`, `docker/scripts/`, and three named extras, so neither shellcheck
   nor the 3.9 grammar check ever sees the test files. Should the lint's
   discovery roots grow, or is the CI unittest step on 3.9 enough?
6. **`make check` does not prove 3.9 compatibility locally.** This host's
   `python3` is 3.10.12. Only the CI step, on `actions/setup-python` 3.9, proves
   it. The tests were written to 3.9 (no PEP 604 unions, no `dict[str, str]`
   annotations, `typing` module throughout), but nothing local enforces that.
7. **`compose-command` accepts any unknown argument silently** and treats it as
   the default mode. Pinned. A stricter port would exit 2 on `--bogos`, which
   would be a user-visible change.
8. **`make check` leaves `tests/host/__pycache__/` behind**, which `.gitignore`
   does not cover, so it shows up as untracked in every subsequent
   `git status`. It was deleted before this commit rather than ignored, because
   `.gitignore` is outside this stage's allowed files. One line
   (`__pycache__/`) would fix it.
